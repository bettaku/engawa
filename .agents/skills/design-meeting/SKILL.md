# 設計会議

ユーザーが指定した議題について、主担当は提案者兼書記、別のサブエージェントはレビュアーを担当する。出力は日本語。
議題が不明なら確認する。呼び出し例: `$design-meeting 通知配信の再試行設計`。

## 開始前

1. `git status --short --untracked-files=all` を確認する。未コミットの変更があれば、ファイルを変更せず、その内容とクリーンな作業ツリーが必要なことを報告して止まる。自動で commit、stash、reset しない。
2. `docs/design/` が `.gitignore` の対象であることを `git check-ignore docs/design/ignore-check.md` で確認する。対象でなければ、設定を勝手に変更せず報告して止まる。
3. 関連コードを読み、議題に対応する短い英語スラッグで `docs/design/<slug>.md` に設計案を書く。背景、現状の問題、提案、代替案、移行手順、ロールバック手順を含める。同名の設計書がある場合は内容を読み、同じ議題の続きなら更新し、別の議題なら別名を選ぶ。

## レビュー（最大3ラウンド）

1. 独立したレビュー用サブエージェントを作成し、次の内容を渡す。
   - [design-reviewer](../../../.codex/skills/design-reviewer/SKILL.md) のパスと、その指示に従うこと。
   - 設計書のパス、議題、ラウンド番号。
   - 設計書と実際のコードを照合し、指摘ID・重大度・根拠を返すこと。ファイルは変更しないこと。
   - 例: 「`.codex/skills/design-reviewer/SKILL.md` に従って `docs/design/<slug>.md` をレビューして。ラウンド1。」
2. レビュー完了を待ち、各指摘をIDごとに「採用」「反論（理由付き）」「要判断」に分類する。採用分を設計書に反映する。
3. 2ラウンド目以降は同じサブエージェントに継続依頼する。更新した設計書と、前回の各指摘IDの分類・反論理由を渡す。取り下げられていない指摘を追跡し続ける。
4. レビュアーの総評が「重大度・高の未解決指摘：なし」となった場合、または3ラウンド完了時に終了する。主担当の判断だけで未解決指摘を解決済みにしない。

利用可能なサブエージェント機能で作成・継続・完了待機を行う。Claude 固有の `codex:codex-rescue` は使用しない。サブエージェント機能が利用できない場合は、独立レビューを行えないことと設計案の保存先を報告し、自己レビューを独立レビューとして扱わず止まる。

## 終了時

- 設計書末尾に「議事録」を追記し、ラウンドごとの指摘ID、重大度、対応分類、反論理由、解決状況を記録する。3ラウンド終了時に残った重大度・高の指摘は「要判断」として残す。
- `git status --short --untracked-files=all` で変更・新規ファイルが何も表示されないことを確認する。`docs/design/` は無視対象なので設計書は表示されない。想定外の変更があれば削除や差し戻しをせず報告する。
- 実装には進まず、ユーザーには設計書の保存先と「要判断」事項を報告する。要判断事項がなければ「なし」と明記する。
