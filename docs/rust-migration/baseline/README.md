## 2. 何を測るか

移行計画 §8.3 の合否基準のうち、Rust移行の前に基準値が必要なものを測る。

| 指標 | 定義 | 計画の基準 |
| --- | --- | --- |
| 応答時間 | エンドポイント別の p50・p95・p99（k6、計測区間のみ） | 基準比で10%を超える悪化がない |
| エラー | 2xx以外の割合。到着率を処理しきれず送れなかった要求（取りこぼし）は別に数える | 5xx率の増加が0.1ポイントを超えて続かない |
| CPU | web コンテナの CPU 時間 ÷ 成功要求数（待機時の使用量を差し引く） | 20%以上の改善を継続投資の仮目標とする |
| メモリ | web コンテナの cgroup `anon` の最大と平均（RSS に近い値） | 同上 |
| DB負荷 | `pg_stat_statements` の実行時間と文の数 ÷ 成功要求数 | 全体コストに併記する |

同じ要求を Rust で処理したときに、同じ環境・同じスナップショット・同じ到着率で、この表の値を比べる。

## 3. 計測条件

### 3.1 環境

| 項目 | 既定値 | 理由 |
| --- | --- | --- |
| web | CPU 2、メモリ 2GB、`clusterLimit: 1`、`NODE_ENV=production` | 1プロセスにして、要求あたりの CPU を割り出しやすくする。レート制限など production だけの処理も含める |
| db | PostgreSQL 15、CPU 2、メモリ 2GB、`shared_buffers=256MB`、`pg_stat_statements` | CLAUDE.md の前提版。本番が別の版なら `BASELINE_PG_VERSION` で合わせる |
| redis | Redis 7、CPU 1、メモリ 512MB、永続化なし | |
| k6 | CPU 2、同じ Docker ネットワーク内 | ホストのポート転送を通さない |
| 到着率 | 固定（constant-arrival-rate） | 応答が遅くなっても負荷が下がらないようにする。飽和は取りこぼしで分かる |
| warm | 同じ到着率で20秒流してから60秒測る | |
| cold | web・db・redis を再起動した直後に60秒測る | Docker VM のページキャッシュは残る（制約） |
| レート制限 | k6 が仮想利用者ごとに `X-Forwarded-For` を変え、`trustProxy: true` で受ける | 本番と同じく利用者・IP単位で働かせ、1つのIPに全要求が集まって429になるのを避ける |

上限の値は、比べる計測の間で変えない。値は結果の `.env` ファイルに残る。

### 3.2 データ

`seed.mjs` が公開APIだけで投入する。DBへ直接書かないので、カウンタ・outbox・キャッシュの更新も本番と同じ経路を通る。投入時だけ `NODE_ENV=development` で起動してレート制限を外す。

| 規模 | 利用者 | ノート | フォロー/人 | 絵文字 | リアクション |
| --- | ---: | ---: | ---: | ---: | ---: |
| small | 50 | 3,000 | 15 | 200 | 3,000 |
| medium | 200 | 20,000 | 40 | 600 | 20,000 |
| large | 1,000 | 100,000 | 80 | 1,500 | 100,000 |

スナップショットは PostgreSQL のダンプ（`snapshots/<規模>.dump`）と Redis の RDB（`snapshots/<規模>.rdb`）の組で、ホームタイムラインの fan-out の一覧やキャッシュも含めて戻す。

ノートは投稿者の偏り（少数の利用者が多く投稿する）、公開範囲（public 70%・home 15%・followers 12%・specified 3%）、返信・Renote・メンション・ハッシュタグ・カスタム絵文字・CWを混ぜる。乱数は固定するが、並行に投入するためIDと順序は実行ごとに変わる。比べる計測は、投入後に取ったDBのスナップショット（`snapshots/<規模>.dump`）から戻して行う。

規模はまだ本番に合わせていない。本番の件数が分かったら比率を合わせる（[test-baseline/README.md](../../../packages/backend/test-baseline/README.md)「規模を合わせる」）。

### 3.3 範囲外

この環境ではまだ測らない。対象の移行フェーズまでに追加する。

- Streaming（WebSocket）の接続数・配信遅延（フェーズ3の前）
- キュー：oldest job age、処理時間、再試行、outbox滞留（フェーズ4の前）
- 連合：inbox の受信・配送（フェーズ5の前。[test-federation](../../../packages/backend/test-federation/README.md) の環境を使う）
- ドライブ・画像処理・検索

## 4. 結果

> **注意（2026-11-25 に判明）:** §4.1〜§4.4 の計測は、スナップショットから PostgreSQL だけを戻し、Redis を空のまま始めていた。そのため、ホームタイムラインなどの fan-out の一覧が Redis になく、`htl_auth` は DB へのフォールバック（`enableFanoutTimelineDbFallback`）の経路で測られていた。Redis も戻すように直した後の `htl_auth` 50rps は、DB 実行が 1要求あたり 0.36〜0.41ms で、§4.2 の 5.29ms の1割以下になった。§4.2 の `htl_auth`・`mix` の値と、§4.4 の CPU の内訳は、本番の通常の経路の値ではない。匿名の参照（`emojis_anon`・`meta_anon`・`notes_show_anon`・`users_show_anon`）と `ltl_anon` は fan-out の一覧を使わないので影響は小さいが、Redis のキャッシュが空から始まった点は同じである。基準値はチャートの修正後にすべて取り直す。→ 2026-11-27 に取り直した（§4.5）。

- **Engawa のメモリ（master＋worker の RSS）は 850〜960MiB。** コンテナ全体ではこれに `pnpm run` の起動ラッパー約250MiB が加わる。

### 4.2 2回目（2026-11-25、合成負荷・small、各条件の中央値）

条件は4.1と同じ。4.1の後に次を直してから測った。

- `notifications_auth` の失敗率100%は、利用者ごとのレート制限（`i/notifications` は 30回/30秒）が原因だった（1人に41回送り、31回目から429になることを確認）。k6 が仮想利用者の番号で利用者を選んでいたため、到着率が低いと少数の利用者に要求が集中した。認証付きの要求は毎回ランダムな利用者で送るようにし、1人あたり制限の80%を超える到着率は始める前に止めるようにした（small の50人では 40rps が上限）。
- cold の CPU は、計測後の10秒の待機区間を差し引くようにした（計測前の待機区間には起動直後の処理が入る。待機時の CPU は計測前 0.13 コア、計測後 0.075 コアだった）。
- 到着率 50rps は3回測り、疑わしい計測（web が 1コアに10秒以上張り付いた、取りこぼしか失敗が1%を超えた）を除いた中央値を取る。1回ずつの値は `results/runs.md` に残す。

除いたもの:

- `emojis_anon` の 25rps と 50rps×3 の最初の4本は、別の作業（PR #399）の `docker build` と同じ Docker VM で重なったので除き、全体の後に web を再起動して測り直した（表の値は測り直した分）。50rps の3回は p95 6.1〜6.3ms、CPU 4.5〜4.6ms/要求でよくそろった。
- **`htl_auth` 以降の warm（`htl_auth`・`i_auth`・`notifications_auth`・`mix`）は参考値。** web を再起動せずに9シナリオを続けて測ったため、後半ほど web の状態が前の計測の影響を受けている。`htl_auth` 50rps の2本目と 100rps、`mix` 50rps の2本目で、web が 1コアに張り付いて要求が詰まった（§4.3）。

### 4.3 web が 1コアに張り付いて要求が詰まる現象（原因特定済み・#401 で修正済み）

4.1 の `i_auth` 25rps と、4.2 の `htl_auth`・`mix` で起きた。どれも同じ形をしている。

- web コンテナの CPU が 1.00 コア前後に数十秒張り付く。DB と Redis の CPU はほぼ 0 のまま。
- web のメモリ（cgroup の anon）が増えては減るのを繰り返す。
- 要求は詰まり、p50 は数ms のまま p90 以上が数十秒になる。web のログでは TypeORM が「query is slow: execution time: 30432」と出すが、`pg_stat_statements` では同じ文の実行時間は短い。TypeORM の計測にイベントループの停止時間が含まれているためで、止まっているのは Node のプロセスである。

既定の設定では、HTTP は master プロセスがすべて受け、worker プロセスはジョブキューだけを処理する（[master.ts](../../../packages/backend/src/boot/master.ts)、[worker.ts](../../../packages/backend/src/boot/worker.ts)）。計測中の master の最大 RSS は 835MB で、V8 のヒープ上限は1プロセス 1,120MB だった。

**GC が原因という仮説は、2026-11-25 の確認で否定された。** web を `--trace-gc` 付きで起動し（[compose.gc.yml](../../../packages/backend/test-baseline/compose.gc.yml)、集計は [gc-report.mjs](../../../packages/backend/test-baseline/gc-report.mjs)）、`htl_auth` を 50rps で15分流した。

- master のヒープ（GC 後の使用量）は 250〜394MB で、上限の 1,120MB に近づかなかった。15分で mark-compact は43回、GC の停止の合計は 8.9秒（全体の約1%）、1回の最長は 110ms。GC 以外に使えた時間の割合（mu）は最低でも 0.965。
- この間も、短い張り付きは起きた。1秒ごとの web の CPU は大半が 0.2〜0.3 コアだが、合計約36秒は 0.9〜1.5 コアに上がり、そのとき要求が詰まった（p99 932ms、最大 4.5秒、取りこぼし157）。数十秒続く張り付きは、この15分では再現しなかった。
- master の RSS は 680MB で、ヒープ（最大 394MB）との差の約300MB はヒープの外（Buffer、ネイティブのメモリなど）にある。

したがって、張り付いている間に master が使っている CPU は GC ではなく、JavaScript の処理（定期処理か、一部の要求の処理）である。何がそれを使っているかは、CPU プロファイルで確かめる必要がある。

**起動したばかりのプロセスでは再現しなかった（2026-11-25）。** web を再起動し、インスペクタ経由で master の CPU プロファイルを取りながら（[compose.prof.yml](../../../packages/backend/test-baseline/compose.prof.yml)、[prof-capture.mjs](../../../packages/backend/test-baseline/prof-capture.mjs)、集計は [prof-report.mjs](../../../packages/backend/test-baseline/prof-report.mjs)）、`htl_auth` を 50rps で10分流した。CPU を85%以上使い切った秒は1秒もなく、p99 は 85ms、取りこぼしは0だった。これまでに張り付きが出たのは、どれも web を再起動せずに何本も計測を続けた後のプロセスである（大きな張り付きは約20本の後、15分の計測の短い張り付きは約5本の後）。プロセスが長く動いて何かが溜まることが条件になっている可能性が高い。

あわせて分かったこと:

- `--cpu-prof` は終了時にしか書かない。10分の負荷の後、master は SIGTERM を受けても60秒以内に終了処理を終えず、強制終了された（起動直後に止めたときは1秒以内に終わった）。長く動いた後の終了処理の遅れは、§9 の切り戻し（旧版での再開15分以内）に関わるので、別に調べる。

**原因: チャートの保存（2026-11-25 の soak で特定）。** web を再起動せずに全シナリオを3周（約75分）流し、master の CPU プロファイルを10分ごとに取った（[soak.sh](../../../packages/backend/test-baseline/soak.sh)）。3周目の `meta_anon`（p99 19.8秒、取りこぼし810）と `htl_auth` で張り付きが再現した。`meta_anon` の張り付いた20秒間、master の CPU の 95.4% は [chart/core.ts](../../../packages/backend/src/core/chart/core.ts) の `saveBuffer` の中の `update` で、その 99.5% が次の1行だった。

```ts
(finalDiffs[k] as string[]) = (finalDiffs[k] as string[]).concat(v);
```

- 認証付きのタイムライン（`notes/timeline`・`local-timeline`・`hybrid-timeline` など）は、要求ごとに `activeUsersChart.read(me)` を呼び、利用者のIDを1件ずつバッファに積む（`read` と `registeredWithin*` の配列。重複を除かない）。
- バッファは20分ごとに保存される（[ChartManagementService.ts](../../../packages/backend/src/core/chart/ChartManagementService.ts)）。保存の `update` は、積まれた件数だけ `concat` で配列を作り直すので、件数の2乗に比例する。手元のベンチマークでは、5,000件 40ms、10,000件 143ms、20,000件 649ms、40,000件 4.3秒（4キー分）。
- この処理は同期的で、HTTP を受ける master のイベントループを止める。web のログの「activeUsers」の保存の開始から「Updated」までは、10分の `htl_auth` 50rps（約31,000要求）の後で **4分31秒**、soak の各周の後で 15〜22秒だった。認証付きのタイムラインの要求がなかった20分間は「Write skipped」で、張り付きは起きない。
- これまでの張り付きは、どれも20分ごとの保存の時刻と重なっていた。シナリオそのもの（`meta_anon` など）とは関係がない。起動直後の10分の計測で再現しなかったのは、計測の区間に保存の時刻が入らなかったためで、プロセスが長く動いたことは条件ではなかった。
- 終了処理の遅れも同じ原因である。終了時の `dispose()` はすべてのチャートを保存するので、10分の負荷の直後は保存に数分かかり、60秒で強制終了された。**このとき、バッファにあったチャートのデータは失われる。**

影響と扱い:

- 本番でも、20分間の認証付きタイムラインの要求の数が数万になれば、HTTP を受けるプロセスが数十秒〜数分止まる。本番のログで「activeUsers」の保存の開始（前の行の時刻）から「Updated」までの時間を見れば、実際に起きているかが分かる。
- 修正（重複を `Set` で除きながら集計し、件数に比例する処理にする）は Rust 移行とは別の不具合修正として扱う。修正の前後で、Node 版の基準値（特に p99）が変わる。基準値は修正後の版で取り直す。修正は #401 で入り、§4.5 で取り直した。取り直した約2時間の間に、web が 1コアに張り付いた計測はなかった（20分ごとの保存の時刻を何度か通っているが、保存の時間そのものは記録していない）。
- 修正までの計測では、張り付きの印が付いた計測を中央値から除く（§4.2 の方法のまま）。20分ごとの保存に重なった計測は、張り付きの検出で除かれる。

idle を除いたサンプルでの割合。**Redis が空で DB へのフォールバックの経路を通った計測である（§4 冒頭の注意）。** `htl_auth` は1要求で約13文の SQL を実行し、master の CPU の約6割が TypeORM と pg ドライバで使われている。Engawa 自身のコードは1割に満たない。関数単位で多いのは pg の `parseRow`（10.2%）、TypeORM の `transformColumns`・`transformRawResultsGroup`（合わせて10.5%）、`replacePropertyNamesForTheWholeQuery`（3.7%）。Rust 版で同じ要求を処理するとき、改善が見込めるのは主にこの部分である（言語よりも、ORM を通さずに必要な列だけを読むかどうかの影響が大きい可能性がある。移行計画 §1 の「既存実装の改善案とも比較する」に当たる）。
